# Database

PostgreSQL 16 is the system of record (ADR-3). Redis is never the only copy of
anything. The schema lives in `prisma/schema.prisma`; every change is a checked-in
migration under `prisma/migrations/`.

## Roles

| Role          | Used by                             | Privileges                                                      |
| ------------- | ----------------------------------- | --------------------------------------------------------------- |
| `Solace`     | migrations, seed, break-glass admin | owner of every table                                            |
| `Solace_app` | the running API (`DATABASE_URL`)    | `SELECT, INSERT, UPDATE, DELETE`, minus the append-only revokes |

The runtime never connects as the owner. That is what makes the append-only
guarantee real: even a compromised service process cannot rewrite consent or
audit history. `MIGRATION_DATABASE_URL` exists so `prisma migrate` can run as the
owner while `DATABASE_URL` stays restricted.

Migrations run as `Solace` because `ALTER TABLE ... GRANT/REVOKE` requires
ownership. Never point `DATABASE_URL` at the owner role.

## Append-only tables

Enforced in `20261024151456_append_only_grants` by revoking `UPDATE`, `DELETE`
and `TRUNCATE` from `Solace_app`:

- `consent_records`
- `alert_events`
- `access_log`
- `crisis_events`
- `safety_team_flags`
- `ai_scans` (metadata only, no journal text)

`test/integration/append-only.spec.ts` proves this by attempting the operations
as `Solace_app` and expecting SQLSTATE `42501`. If you add a table that stores
history, revoke the same privileges in its migration and add it to that test.

`update`, `delete` and `truncate` on these tables still work for the owner role.
That is intentional for migrations and for a supervised legal erasure process,
and it is why the owner credentials are not deployed with the service.

## Naming and types

- `snake_case` in the database, `camelCase` in Prisma, via `@map`.
- `uuid` (`@db.Uuid`) primary keys, generated by the database default
  `gen_random_uuid()`.
- Timestamps are `timestamptz`-equivalent `DateTime` in UTC. Never store local
  time. `*_at` is the suffix.
- Client-originated writes carry `client_id` (UUID) and `client_created_at`, with
  `@@unique([userId, clientId])`. This is the idempotency key for offline sync.
- Encrypted columns are `*_ciphertext` with a sibling `key_id`. No plaintext
  column exists for the same data.

## Encryption at rest (ADR-6)

Application-level AES-256-GCM for: journal text, safety-plan fields 1–5,
therapist licence number. Each row stores `key_id` so keys can be rotated
without a flag day. The key itself is resolved from
`FIELD_ENCRYPTION_KEY_REF`; it is never in the database or the repository.

CP1 builds the `KeyProvider` and the AES-256-GCM helpers, and uses them for
safety-plan fields 1–5. The therapist licence number uses them in CP3 and journal
text in CP4. Key rotation and the re-encryption job are CP4–CP5 work. Every row
records the `key_id` it was written with, so rotation never needs a flag day.
Until a column is wired to a repository, no code writes plaintext to it because
no code writes it at all.

Ciphertext layout is `base64(iv[12] || authTag[16] || ciphertext)`. The AAD binds
the value to `table:column:row_id`, so copying a ciphertext into another row
fails to decrypt. The local provider accepts `dev://` and `test://` refs only
outside production, and `env://VAR` (base64, 32 bytes) anywhere. A KMS adapter is
blocked on OD-8.

## Retention and deletion

| Data                       | Retention                  | Deletion path                                |
| -------------------------- | -------------------------- | -------------------------------------------- |
| Consent records            | indefinitely (legal proof) | never deleted                                |
| Crisis events and alerts   | 24 months                  | hard delete by scheduled job after retention |
| Access log                 | 24 months                  | hard delete after retention                  |
| Journals, check-ins, tasks | until account deletion     | cascade from `users`                         |
| Audit of a deletion        | kept                       | `deletion_requests` row stays, PII removed   |

Deletion is two-step (`deletion_requests`): request, then confirm. The account
enters `deletion_pending` and is processed asynchronously. Foreign keys on
crisis history use `Restrict`, so an account with retained crisis history cannot
be hard-deleted by accident; the job anonymises the user row and keeps the
retained records.

## Migrations

```bash
npm run db:generate        # regenerate the client after a schema edit
npm run db:migrate         # dev: create + apply locally (prompts for a name)
npm run db:deploy          # staging/production: apply committed migrations only
```

Rules:

1. Migrations are forward-only and reviewed like code.
2. A migration must not drop a column in the same release that stops writing it.
   Two releases: stop writing, then drop.
3. Never edit an applied migration. Add a new one.
4. Any migration that adds an append-only table must also add the revokes and
   update the integration test.
5. `db:deploy` runs before the new app version starts. A migration must be
   compatible with the previous app version during the rollout window.

## Seed

`npm run db:seed` writes synthetic fixtures only and refuses to run when
`NODE_ENV` is `staging` or `production`. Emails use the reserved
`example.invalid` domain.
